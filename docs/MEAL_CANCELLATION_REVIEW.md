# 便當退單申請與審核

日期：2026-10-08
狀態：本機程式已完成，尚未部署。正式站目前行為不因本文件改變。

## 使用者操作

在「便當訂單」選擇原訂單，按「申請取消這筆便當」、填寫原因並送出。申請等待管理員審核時，訂單仍有效，款項、發票與可售份數不變，取餐憑證依原訂單狀態有效。

同一張訂單只能有一筆待審申請。重複送出會回傳原申請，保留最初原因。使用者能看到申請原因、申請時間、審核結果、管理員理由及審核時間。拒絕後，尚未結束履約的訂單可補充原因重新申請；歷史申請仍保存。

## 管理員操作

進入 `/admin/meals` 的「退單審核」分頁，預設列出待審申請，可依狀態、訂單編號或 Email 搜尋並分頁。明細包括取餐時間、餐點與客製、份數、金額，以及付款、履約與發票狀態。

管理員選擇核准或拒絕，填寫買家可見的審核理由後確認。核准會取消整張訂單；拒絕保留原訂單。結果保存操作者、理由與時間，並建立稽核及買家通知。已審核申請重複送出相同結果不會再次執行，改為相反結果回應衝突。

場次訂單同步顯示「退單待審，訂單尚未取消」。待審不自動暫停廚房作業；目前仍需管理員依現場情況協調。

## 訂單、退款與發票

| 審核／訂單狀態 | 訂單處理 | 份數處理 | 發票處理 |
| --- | --- | --- | --- |
| 申請待審 | 保留原訂單 | 不釋放 | 不變 |
| 拒絕 | 保留原訂單 | 不釋放 | 不變 |
| 未付款核准 | 取消履約、付款標為逾期 | 釋放有效保留 | 不新增開票或作廢 |
| 已付款、未製作核准 | 取消履約、建立原通路退款 | 釋放已付款份數 | 等退款確認 |
| 製作中／待取餐核准 | 取消履約、建立原通路退款 | 保留已製作份數，不重新販售 | 等退款確認 |
| 已取餐、逾時未取或供餐結束 | 不允許本流程核准，可拒絕結案 | 不變 | 不變 |

雷門退款建立後先顯示 `refund_pending`，不代表買家已收到退款。退款結果經後端確認後才轉 `refunded`，並沿用既有全額退款後發票調整流程。汎宇票先轉 `void_pending`，查回供應商已作廢才轉 `voided`。部分退款、非汎宇及帳戶來源不明的情況，保留既有人工流程。

製作中／待取餐核准時保存 `OrderFulfillment.meal_capacity_retained=true`，後續退款補查也不恢復已製作份數。核准當下無法建立有效退款工作時回應衝突，申請仍待審，訂單及份數維持原狀。

審核與取餐先鎖定同一筆訂單並重新讀取履約狀態；已核銷取餐不能被隨後核准取消，已取消訂單不能再核銷。晚到付款仍沿用既有取消訂單補查／退款處理。

## API 與資料升級

| API | 行為 |
| --- | --- |
| `POST /v1/meal-orders/{id}/cancellation-requests` | 本人建立申請，原因必填；201 |
| `POST /v1/meal-orders/{id}/cancel` | 舊端點保留，但改為只建立申請；201，不再直接取消 |
| `GET /v1/admin/meal-cancellation-requests` | 管理員查詢；支援 review_status、search、limit、offset |
| `POST /v1/admin/meal-cancellation-requests/{id}/review` | 管理員填 decision=approve/reject 與 reason；成功 200，衝突 409 |

一般 `/v1/orders/{id}/cancel` 也不能讓便當買家繞過審核。普通商品與團購沿用既有取消規則。

Migration `0019_meal_cancellation_review` 依賴 `0018_member_invoice_tax`，新增審核表與已製作份數保留欄位，舊履約資料預設 `false`。資料庫限制一單一筆待審，且完成審核必須保存操作者、時間及理由。有審核歷史時拒絕降版刪表，以保留稽核資料。

部署須從核對過的正式版本隔離移植相關修改，先備份、升級資料庫，再發布 API 與 Web。舊 Web 的取消請求也會變成申請，但舊回應與提示不相容，前後端須協調發布。本次未修改正式資料庫、未發起真實退款／開票／作廢。

## 驗證與界線

測試涵蓋本人權限、原因驗證、拒絕後重申請、重複核准、退款建立失敗、製作份數保留、退款確認後汎宇查票—作廢—查回、取餐衝突、搜尋分頁及 migration 資料保留。外部金流與發票使用模擬回應，不能視為正式交易驗收。

- 完整後端 1,171 項通過；新增晚到付款回歸後，退單專項 19 項另行通過。晚付款會退款，不會復活已核准取消的訂單。
- 前端 58 項測試與 TypeScript／Vite build 通過，API 清單已匯出為 195 路徑。
- 真實 PostgreSQL 18.6 的 5 項並行測試通過：重複申請、多管理員核准、核准與取餐兩種先後順序、相反決定競爭。
- SQLite 升降再升與舊訂單／份數快照保留、審核歷史降版保護通過。隔離 PostgreSQL 的升降再升及新表／欄位比對通過；比對時排除現有三個快取欄位的純註解差異（orders.order_kind、orders.fulfillment_status、users.membership_type），不更改這些舊欄位。
- PostgreSQL 只使用 `/private/tmp` 獨立測試資料庫，測試後已停止；正式資料庫與本機原資料庫未執行升級。

瀏覽器畫面與互動驗收仍待完成；先前本機預覽受工具安全政策阻擋。本批直接修改專案，不新增示意頁。部分品項退單、已交付的例外退款、廚房硬體取消單與重新出單仍屬後續範圍。提前一天及新午晚餐時段規則尚未套用。
