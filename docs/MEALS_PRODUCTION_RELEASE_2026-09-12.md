# 便當正式付款、取餐與發票發布

日期：2026-09-12

## 授權與範圍

本次經使用者同意，沿用 Render 服務與原有個資加密金鑰，啟用便當正式收款、取餐碼、汎宇發票。其他新交易及入社收費暫緩；不開賣展示場次，不自行建立正式付款、扣款、退款或開票測試。

本版從既有已部署版本 c2ae6ab 隔離整理，不納入原工作區其他尚未發布的變更。未修改依賴、Render Blueprint、既有 JWT／PII 金鑰、資料保留政策或名冊。不得重新套用舊 preview Blueprint 覆蓋這次正式服務設定。

## 執行規則

- `APP_ENV=production`、`SALES_SCOPE=meals_only`。只接受有效便當場次、場次餐點與現場取餐訂單；三個展示場次持續禁止正式下單付款。
- RayGate 正式模式與已驗證合約；驗收用 SKU、訂單 ID 均須空白。保留既有回呼、補查、退款處理。
- 汎宇正式 API 為 `https://api01.einvoice.com.tw/einv`，使用供應商核對的 API 傳輸帳號，不是 WEB 平台登入帳號。正式密碼與 API key 只放 Render，不存 Git 或筆記。
- 開票帳戶／環境與訂單綁定。migration 0014 僅增加可空欄位，不回填旧訂單；缺少綁定或與目前帳戶不符時停止新付款及開票，避免舊測試單誤送正式平台。
- 付款成功才顯示有效取餐碼；重複核銷、取消、退款與失效場次均不能取餐。發票待處理不阻止已付款取餐。
- 付款返回頁先完成付款確認，再以本人便當訂單查詢驗證後轉回該張便當訂單，避免管理員訂單清單造成錯誤導向。
- 保留每 60 秒既有背景對帳；這次不手動重送舊工作。正式場次日期、時段、地點與供應數量仍待合作社確認，9/14 只是暫定。

## 發布前驗證

- 隔離發布版 SQLite 後端與稽核：902 passed。
- 前端／API 契約：31 passed；TypeScript、Vite production build 通過。
- Chromium 便當及既有付款返回：18 項模擬 API 案例；最終結果與雲端 PostgreSQL／部署收據於實際完成後另記。
- API 路由仍為 180；資料庫僅加入 0014，可空帳戶綁定欄位。

## 發布順序與驗收界線

先推送帶 `[skip render]` 的已測版本，待 CI 的 PostgreSQL migration、並行交易與前後端測試成功，再儲存正式服務設定並部署同一版本。服務健康與展示場次防護檢查不會建立交易。

自動化與模擬測試不代表真實付款到正式開票的整筆驗收已完成。正式場次啟用後由使用者本人付款，再核對取餐碼、核銷與正式發票。原有 PII 金鑰不得重新產生或輪替。
