# 便當後台訂單查詢與待辦

日期：2026-10-08
狀態：本機完成，尚未部署；不改訂餐、退款、發票或會籍政策。

## 管理員操作

進入 `/admin/meals` 預設開啟「訂單查詢與待辦」。輸入編號、姓名或 Email，可搭配取餐日期起迄、餐別、預計取餐時間，以及付款、履約、發票、最新退單狀態，按「查詢訂單」套用。日期錯誤會提示，後端也拒絕非法條件；清除篩選會回到全部訂單。

每頁 20 筆，依下單時間由新到舊排序（2026-11-06 調整，詳見 [查詢排序規則](QUERY_SORTING.md)），展開查看餐點、客製、稅別、票號及退單原因。待審訂單可直接開啟該筆審核；退款／發票入口會帶原訂單編號前往 `/admin?q=...`，減少重新輸入與找單。查詢不會直接執行退款、作廢或核銷。

數量與清單每 30 秒更新，也可手動重新整理。取餐核銷、取消場次、退單審核、退款及發票處理後會刷新相關查詢。若目前分頁因待辦結案而超出範圍，會調整到最後有效頁。

## 待辦定義

| 待辦 | 計數條件 |
| --- | --- |
| 退單待審 | 仍有 pending 退單申請，包含已結束履約但尚需拒絕結案的申請 |
| 退款待處理 | 訂單退款中／晚付款待退款，或存在待退款；失敗退款在訂單尚未完全退款時列入。原訂單仍已付款的重複付款退款也會列入 |
| 發票待處理 | 發票開立失敗、保存的供應商錯誤、未開立完成的開票失敗工作，或未作廢完成的調整失敗工作。原票仍已開立但作廢工作失敗也列入；成功開票後的舊開票失敗、已作廢的舊錯誤不再次計入 |
| 今日待取餐 | 台灣今日取餐、已付款、未取消、仍可履約、場次未結束或取消，且未超過取餐結束時間 |

待辦涵蓋全部便當，不受表單日期影響。點選待辦清除先前條件後套用對應清單；可再加條件查詢。數字是訂單數，單張訂單即使有多個錯誤或退款工作也只算一次，不代表金額或餐點份數。

## 時間與歷史資料

日期與 HH:MM 皆為台灣時間，日期迄以隔日 00:00 為不包含上界。優先使用保存的 pickup_at；舊訂單缺值才依場次開始時間，介面會明示。跨午夜依實際預計取餐日期判斷，不沿用場次 service_date。

有 lunch／dinner 標記的場次可依餐別搜尋，未標記的舊手動場次顯示並可搜尋「未標餐別」，不根據名稱或時間猜測。退單狀態依最新申請判定，舊拒絕紀錄不覆蓋新的待審申請。

## API 與實作

- `GET /v1/admin/meal-orders`：只向管理員開放，支援 search、date_from、date_to、meal_period、pickup_time、payment_status、fulfillment_status、invoice_status、review_status、work_queue、limit、offset；回傳分頁及訂單明細。
- `GET /v1/admin/meal-operations-summary`：回傳台灣今日日期及四項待辦數字。
- 主要查詢在 `backend/app/meal_operations.py`。以存在子查詢判定待辦，避免多退款／申請／工作記錄將訂單列數放大；搜尋會將 % 與 _ 當字面文字處理。
- 不新增資料表或 migration，不修改正式或原本機資料。保留既有退單、金流、發票與取餐的動作入口及權限。
