# 便當現場付款與對帳

日期：2026-10-21

本次範圍由使用者確認為便當預訂。程式在 `codex/line-member-onsite-payment` 本機開發，尚未推送或部署，沒有操作真實收款、退款、發票或取餐核銷。

## 操作

1. 後台「便當營運管理」→「場次與核銷」，勾選該場的「開放合作社現場付款」。預設關閉，只影響新預訂；既有訂單仍可確認收款。
2. 買家選「合作社現場付款」，填訂單通知 Email 並確認預訂。此時訂單為未付款，保留餐點至場次取餐結束，沒有付款交易、收入、積點或有效取餐碼。
3. 後台「訂單查詢與待辦」、本場訂單及一般訂單管理皆有收款入口。選「標記已付款」，填實收金額、處理原因、現金／POS／現場 QR Code 與選填參考單號，再確認實收。
4. 確認後才建立 `provider=onsite` 的付款紀錄、付款時間、積點與操作稽核。買家取得取餐碼，工作人員仍須另外核銷取餐。
5. 誤標且尚未交餐、尚未進入退款時，可「更正為未付款」，保留原收款與更正證據，同步回復保留份數、移除有效收款金額並沖銷積點。重新確認只建立一筆有效收入。
6. 真正取消及退款沿用退單申請與管理員審核；已收款單先進入待退款，實際線下退還後按「確認現場退款」。更正未付款不代表退款。

現場 QR Code 是合作社既有收款方式；App 只記錄工作人員核對結果，不產生收款碼或自動向外部支付平台查帳。

## 發票分工

現場付款使用 `invoice_status=external`，代表發票由合作社現場 POS 處理，不代表 App 已查證開票。App 在收款、取餐、未取餐及退款時均不排程線上開票／作廢，直接要求線上開票也會拒絕，避免重複開票。POS 發票的開立與退貨作廢由合作社現場作業完成。

線上付款保留既有金流及電子發票流程。

## API 與資料

- `PATCH /v1/admin/meal-events/{event_id}/payment-options`：切換現場付款。
- `POST /v1/orders/{order_id}/admin/cash-payment`：確認已付款。
- `POST /v1/orders/{order_id}/admin/cash-unpaid`：更正誤標為未付款。
- `POST /v1/orders/{order_id}/admin/cash-refund`：確認已線下退款。

收款輸入為 `amount`、`reason`、`collection_method`（`cash`／`pos`／`qr`）及選填 `reference`。後台便當查詢回傳 `onsite_payment`，包含方式、時間與參考單號。各次修改保留 `AdminAudit`；原付款更正資訊保存在付款交易的 `payment_correction` 中。

`cash_on_pickup` 與 `/cash-*` 是沿用既有草稿的內部名稱，對外統一稱「合作社現場付款」。一般農產品與團購的現場付款、本機以外的貨到付款不在此次範圍。

## 發布與驗證

Migration `0029_onsite_payments` 接在 `0028_financial_statements` 後；既有訂單預設 `online`，既有場次預設不開放現場付款。已有現場付款訂單時禁止降版移除欄位，應向前修復。

覆蓋收款冪等、權限、金額、份數、誤標更正與重收、積點、實收報表、線下退款、逾期釋放、已取餐阻擋更正及 POS 不重複開票。PostgreSQL 競爭測試需獨立的本機 `TEST_POSTGRES_URL`，未提供時會跳過，不視為已驗證資料庫競爭。
