# UI 與使用流程審查

日期：2026-10-23。審查基準：`5c061a7`，目前正式版 Vite 前端 `web/src`。本報告只有審查與建議，沒有修改應用程式。

## 先處理這五項

| 順序 | 項目 | 影響 |
|---|---|---|
| 1 | UX-01：團購轉正式時先展示價格、數量、日期 | 管理員目前一鍵送出隱藏的折扣與時程 |
| 2 | UX-02：付款完成橫幅以伺服器查回狀態決定 | 網址參數可以與實際付款狀態矛盾 |
| 3 | UX-03：發票欄位顯示具體阻擋原因 | 錯誤統編、空公司名、錯誤手機載具會讓付款按鈕無聲失效 |
| 4 | UX-04：返回商品／團購時保留分頁 | 已在正式站重現：返回選品卻進便當頁 |
| 5 | UX-05：購物清單價格與正式試算一致 | 一般買家會看到社員單價與一般價合計並列 |

P1 表示可能造成錯誤商業操作、優先修正；P2 表示特定正常情境下流程失敗或誤導；P3 表示次要品質改善。「來源確認」表示可由控制流程直接推出，沒有在正式站故意製造錯誤或改資料；「實測」表示已在正式站唯讀導航重現。

## 已確認缺陷：交易與導航

### UX-01 · P1 · 轉正式團購直接採用未顯示的商業條件

**來源確認。** `web/src/pages/AdminGroupsPage.tsx:69` 的 `convert` 直接送出 `campaignPayloadFromTarget`；第 84 行「建立正式團購」沒有條件預覽。第 136–139 行自動套社員價 92 折、一般價 95 折、每人上限 5、供應量取需求量與門檻三倍的最大值，付款截止設為七天後，取貨設為十至十一天後。

觸發：管理員將已達門檻的需求投票轉成正式團購。影響：管理員沒有確認折扣、供應商承諾或取貨時間，就發布可付款條件；這些是實際交易資料，並非單純顯示預設值。

建議：開啟與「直接開團」共用的可編輯表單，預填合理值，讓管理員確認價格、成團門檻、供應量、截止與取貨區間後提交。驗收：點轉正式先見到完整條件，不產生團購；確認後請求內容與畫面一致。

### UX-02 · P2 · 付款成功橫幅仍信任網址結果

**來源確認。** `web/src/pages/OrdersPage.tsx:139` 在沒有已刷新結果、且非指定 confirming 情況時，退回使用 `search.result || search.payment || search.logistics`；第 408–424 行將 `paid`／`succeeded` 顯示成「線上付款已完成」「付款已由金流查詢確認」。

觸發：開啟保留 `result=paid` 的舊網址，或直接帶此參數，但目前訂單尚未付款、已取消／退款，甚至尚未查到所指訂單。影響：頁首成功結論可能與訂單卡狀態矛盾。此問題不代表後端會因此改成已付款。

建議：網址只指向訂單並啟動重新查詢；付款結論從該訂單及付款 attempt 的已確認狀態推導。資料未到時顯示確認中，找不到時顯示找不到，不預告付款成功。

### UX-03 · P2 · 發票驗證只停用按鈕，沒有指出錯誤欄位

**來源確認。** `web/src/components/InvoicePreferenceFields.tsx:31` 驗證統編檢查碼、公司名、Email 與手機載具；第 81–91 行手機條碼、第 196–216 行統編／公司名沒有錯誤狀態或錯誤文字，只有 Email 在第 149–156、219–235 行提供。`web/src/pages/CheckoutPage.tsx:177`、`GroupCampaignPage.tsx:143` 及便當結帳都以此結果停用提交。

觸發：填入八碼但檢查碼錯誤的統編，或漏公司名、載具格式錯誤。影響：使用者看到付款按鈕不可點，無法辨別是哪個欄位阻擋。

建議：共享一份欄位驗證結果，對已操作或提交後的錯誤顯示具體原因，配對 `aria-invalid`／`aria-describedby`；提交區可指出第一個待完成欄位。這是 `web/AGENTS.md` 允許保留的「當下驗證錯誤／阻擋原因」，不應用 FAQ 取代。

### UX-04 · P2 · 選品與團購返回連結都重設成便當分頁

**正式站實測＋來源確認。** `web/src/pages/ShopPage.tsx:17` 以本地 state 固定從 `meals` 開始，第 52 行切換不寫網址。`ProductDetailPage.tsx:20` 的「回到合作社選品」、`GroupCampaignPage.tsx:151` 的「回到共同團購」、`HomePage.tsx:101` 的「瀏覽全部選品」都只指向 `/shop`。

實測：日常選品→古早味黑豆蔭油→回到合作社選品，落在「我要訂餐」便當頁。影響：返回目的與文字不符；深連結、重新整理與分享也無法維持正在瀏覽的購物類型。

建議：將 `tab=products|groups|meals` 設為路由搜尋狀態；相關入口指定分頁，從詳情返回保留搜尋／篩選與捲動位置。驗收：三種來源進出詳情都回到原來分頁。

### UX-05 · P2 · 一般買家的清單單價固定顯示社員價

**來源確認。** `web/src/pages/CheckoutPage.tsx:209` 一律渲染 `product.member_price`，沒有社員價標記；右側第 339–342、373–379 行則使用正式試算與實際計價身分。`web/src/pages/GroupCampaignPage.tsx:230` 即使用一般買家的 quote，欄名仍為「社員單價」。

觸發：一般買家購買社員價與一般價不同的商品，或商品在加入清單後調價。影響：左側單價與右側正式計價不一致，容易被理解為加價或算錯。後端試算是否正確須另外判斷，不能由此推論實際錯收。

建議：已試算的清單行使用 quote 單價／小計；試算前明確標記參考價與身分，團購標籤隨計價身分變更。保留目錄卡現有「社員價」標記，避免再增加無標記價格。

## 已確認缺陷：清單與帳號連續性

### UX-06 · P2 · 普通購物車不限制庫存，也長期保留商品快照

**來源確認。** `web/src/context/CommerceContext.tsx:22` 從 localStorage 直接還原完整商品；第 44–61 行增加／修改數量沒有庫存上限。`web/src/components/Shared.tsx:64` 只判斷商品原本庫存是否大於零，不計已加入數量；`CheckoutPage.tsx:203` 使用快照，第 216 行無限加一。

觸發：庫存只剩一件卻連續加入，或隔日帶著舊清單回來，商品價格、庫存、上架狀態已變動。影響：使用者先完成其他填寫，最後才被 quote 擋住，且清單仍呈現舊資料。

建議：持久化商品 ID 與數量，進入清單時對最新商品／quote 調和；每行指出缺貨、下架或數量超限，直接提供調整／移除操作。前端上限只是提早回饋，後端仍維持權威庫存驗證。

### UX-07 · P2 · 結帳轉 Email 註冊後遺失原目的地

**來源確認。** `web/src/pages/LoginPage.tsx:13` 能讀 `return_to`，但第 38 行「註冊帳號」是沒有參數的 `/register`。`RegistrationPage.tsx:15` 使用預設目的地，第 49 行送往驗證頁只保留 Email／token／intent；`AuthFlowPages.tsx:91` 已登入後導向 `/account`，第 150 行驗證完成登入也沒有原結帳目的地。

觸發：未登入的新買家從結帳登入，選擇 Email 註冊並完成驗證。影響：流程最後到社員中心或預設商店，無法自然接續原購物車／便當場次；清單雖可能仍保存，使用者必須自行重新找到。

建議：從登入→註冊→驗證→登入連續傳遞已正規化的站內 `return_to`，驗證成功後回原任務；保留現有避免站外跳轉的正規化邏輯。

### UX-08 · P2 · API 判定登入失效後，畫面仍認為已登入

**來源確認，與架構審查共用議題。** `web/src/lib/api.ts:125` 會嘗試刷新，失敗後第 133 行清除 session；`web/src/context/AuthContext.tsx:40` 只在初始化／sessionAttempt 改變時恢復 user，第 59–84 行僅明確登入／登出更新 user，沒有接收這次 API session 失效。

觸發：已開頁面的登入與 refresh session 都過期，下一次試算取得 401。影響：頁首仍顯示帳號；`CheckoutPage.tsx:330` 的登入入口依 `user` 決定，不會出現，使用者只能看錯誤或自行重新整理。

建議：統一 session 失效事件／store，原子更新 user 與私人查詢快取；保留未送出的購物內容並展示可回原頁的重新登入操作。

### UX-09 · P2 · 非社員直開提案詳情停在無限載入

**來源確認。** `web/src/pages/ProposalDetailPage.tsx:24` 只有 `canAccess` 時啟用 proposal query；第 60 行先判斷 `proposal.isPending`，第 61 行才判斷 `!canAccess`。沒有快取且 disabled 的 query 仍是 pending。

觸發：已登入非社員直接開 `/proposals/:id`，或社員資格查詢失敗。影響：本應顯示「正式社員限定」或錯誤，卻永久呈現骨架載入。

建議：依序處理登入、資格載入／錯誤、權限不足，再處理已啟用的提案查詢。驗收非社員不需等待提案 query 就能看到正確入口。

### UX-10 · P2 · 社員資格查詢失敗被當成尚未入社

**來源確認。** `web/src/pages/SocialPage.tsx:67` 在 pending 後直接檢查 `!isMember`，沒有錯誤分支；相同模式出現在 Activities、Governance、Directory、Wishes。`MembershipApplicationPage.tsx:126` 略過載入後，第 131 行把無 application 資料當 `draft`，即使原因是查詢失敗。

觸發：會員 API 暫時斷線／5xx。影響：正式社員被引導申請入社，既有申請可能被畫成新草稿，將系統故障呈現為資格問題。

建議：共用資格 gate，區分「確認中」「查詢失敗可重試」「已確認無資格」。可沿用 `MeetingsPage.tsx:37` 已有的明確錯誤分支；申請查詢失敗時不渲染新的可編輯草稿。

## 已確認缺陷：團購與操作回饋

### UX-11 · P2 · 已關閉團購仍以可購買的形式導流

**正式站實測＋來源確認。** `web/src/pages/ShopPage.tsx:108` 全部顯示活動，第 112 行直接顯示 intake enum、第 118 行固定「查看並參加」。`GroupCampaignPage.tsx:170` 仍渲染完整取貨／發票／購買表單，直到第 238 行才停用最終按鈕。

正式站可見兩個 CLOSED 團購；進入「台農地瓜共同購買」後看到「此團目前未開放加入」、小計與合計 $0、停用付款按鈕。影響：使用者點進一個被宣告可參加的活動，才發現無法操作；$0 也不能代表真實報價。

建議：以 intake 與成團結果共同決定標籤及 CTA，關閉活動顯示「查看結果」，詳情改成結果／取貨資訊／下一步。報價尚未成立顯示待確認或省略金額，勿渲染假 $0。保留歷史可查詢，不必刪除活動。

### UX-12 · P2 · 團購取貨與截止時間資訊不完整

**來源確認。** `web/src/pages/GroupCampaignPage.tsx:164`「截止時間」只用 `formatDate`，第 165 行只顯示 `estimated_pickup_start`，沒有呈現結束窗口或 `final_pickup_at`。`web/src/lib/api.ts:180` 的日期格式沒有時間、年份、指定時區；第 191 行日期時間也未指定營運時區。

觸發：截止日當天購買；團購已確認正式取貨時間且與原預估不同；使用者裝置在不同時區。影響：無法知道幾點截止、什麼時間可取貨，跨時區可能看到不同日期。

建議：截止顯示台灣完整日期時間；正式取貨時間優先，未確定時顯示預估起迄，跨年歷史保留年份。統一營運時區格式器，沿用便當已有的明確時間處理方向。

### UX-13 · P2 · 團購取貨地點讀取失敗沒有恢復路徑

**來源確認。** `web/src/pages/GroupCampaignPage.tsx:65` 查詢地點，第 117 行只有未選時設定首個；第 186–194 行只 map data，沒有載入／錯誤／無地點處理；第 143–146 行提交條件只看地點 ID 字串，未確認仍存在於目前清單。

觸發：地點 API 失敗或清單更新移除已選地點。影響：前者留下一片空白和不可提交按鈕，後者可能帶著失效 ID 到後端才報錯。

建議：共用普通結帳已存在的地點載入、錯誤重試、空清單與選擇調和邏輯；提交依實際 selected location 而非舊字串。

### UX-14 · P2 · 團購數量控制沒有可讀名稱，選項未完整分組

**正式站可存取樹確認＋來源確認。** `web/src/pages/GroupCampaignPage.tsx:174`、176 的加減按鈕只有圖示，正式站 AX tree 兩個 button 名稱均空白；第 190、200 行 radio 沒有共同 `name`。`InvoicePreferenceFields.tsx:164` 用 button 模擬 radio，但沒有方向鍵／roving tabindex。

影響：螢幕閱讀器無法知道兩個無名按鈕的動作；鍵盤使用者不能依原生單選群組的預期操作。一般結帳雖有名稱，同頁多商品的「增加數量」仍無商品識別。

建議：按鈕提供含商品名的可讀名稱與合理 disabled 上下限；取貨方式／地點採原生具 name 的 radio 或成熟無障礙元件；自製 radiogroup 補全鍵盤行為。驗收以鍵盤及 AX tree 檢查，不只看畫面。

### UX-15 · P3 · 團購投票的資料狀態與 enum 顯示不完整

**來源確認。** `web/src/pages/GroupVotePages.tsx:52` 讀取商品與套組，第 56 行查詢未完成或錯誤都變成空陣列，第 59 行不顯示相應狀態。`ShopPage.tsx:98` 有團購 pending/error，但沒有零筆結果訊息。`GroupVotePages.tsx:62` 與 `AdminGroupsPage.tsx:148` 的提案狀態 mapping 缺少後端 `ended_unmet`、`expired_unhandled`，會落成內部英文值。

影響：新投票只能看到空選單，無法分辨暫時讀不到或真的沒有項目；投票結束原因難理解。

建議：每個資料區分載入、錯誤、空結果並提供合理動作；前後端共享完整狀態型別／標籤檢查，不將未知 enum 當正常使用者文案。

## 設計建議與正式站資料觀察

以下與可證明的流程缺陷分開，尚未因審查擅自改版或下架商品。

| 項目 | 證據與建議 | 優先度 |
|---|---|---|
| 商品資訊先回答購買問題 | `ProductDetailPage.tsx:20` 展示 SKU、稅別、「正式主檔」；`Shared.tsx:49` 每張卡都顯示 SKU。實測長 SKU 佔主要資訊區。建議把版面用在規格、產地、成分／保存、實際取貨限制；必要補充放 `/help`，遵循既有文案規則 | P3 |
| 讓 28 件商品容易找到 | 正式選品清單有 28 件，`ShopPage.tsx:85` 直接鋪全部商品，沒有搜尋／分類控制。建議先加簡單商品搜尋與分類，並與分頁一起保留在 URL | P3 |

## 非便當購買的本次直接證據

正式站「日常選品」可見商品，古早味黑豆蔭油詳情有社員價 $280、一般價 $300、庫存 31 與可操作加入按鈕。既有購物車已有一瓶該商品；打開結帳可成功取得 $280 試算、取貨地點與可用付款按鈕。本次沒有新增清單內容，也沒有按付款。

因此，現有觀察能排除「所有非便當都被目錄 UI 隱藏」；不能排除建立訂單、付款重試或政策開關在後續步驟阻擋。修復驗收應覆蓋「看到→試算→建立自取訂單→建立付款頁→付款返回→取貨」整條鏈，並保留已關閉配送功能的既有邊界。詳細政策根因與自動測試由後端／流程審查報告承接。

## 應保留的既有做法

1. 便當頁已有草稿保存、定期更新可用量／選項、必要選項驗證、數量限制與摘要跳轉；一般購物車可以重用這些成熟互動原則。
2. `checkout-navigation.ts` 先保存可返回訂單的站內歷史，再開外部金流；訂單頁也有查詢付款狀態與重試結構，應修正狀態權威來源而非整段推倒。
3. 取餐憑證依付款與取消狀態控制；取消前有確認，退款與發票狀態分開表達，保留這些交易保護。
4. 全站米色／深綠／黃色、字級設定、skip link、Radix tabs 與多數欄位標籤已有一致基礎；本次桌面實測沒有看到必須整站換風格的證據。

## 建議驗收順序

1. 三個購物分頁的入口／返回／重新整理維持正確位置；目錄每件可售商品的 quote 與政策符合要求。
2. 一般買家與正式社員各走普通商品及便當；檢查清單單價、正式小計、發票錯誤定位、數量超限回饋。
3. 新買家從結帳註冊；既有買家遇登入失效，兩者最後都回原任務且不丟草稿。
4. 團購開放、已關閉、未達標、已成團四種狀態各檢查列表 CTA、時間與詳細頁；管理員轉正式先審閱條件。
5. 在可控制的測試環境模擬失敗與舊付款 URL，最後用 390px 手機、桌面、純鍵盤確認關鍵旅程。不得把正式站成功開頁等同已完成這些驗收。
