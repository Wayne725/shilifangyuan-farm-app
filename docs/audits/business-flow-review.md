# 業務流程稽核

日期：2026-10-23
專案：十里方圓農產品 App
基準：`5c061a7`（正式版 Vite／FastAPI）；商品銷售範圍修復由本次主工作另行處理。

## 結論與範圍

非便當商品被封鎖與 `sales_scope=meals_only` 及測試商品白名單有關；本報告另外驗證一般商品、團購、便當、取消退款、社員活動及治理的流程接縫。確認六項可重現問題／流程缺口，其中團購庫存重開、團購內容變更、背景投票結算與結餘重複分配應優先處理。

本次沒有讀取或修改正式資料，也沒有實際刷卡、退款、寄信或呼叫外部服務。現有測試通過不等於外部供應商與 PostgreSQL 併發已驗收；這兩項仍需獨立環境驗證。

| 流程 | 已檢查內容 | 結果 |
| --- | --- | --- |
| 商品 → 試算 → 建單 → 付款 | 身分計價、下單快照、庫存保留、取貨與配送分離 | 非便當銷售範圍由主工作修復；一般商品沒有便當類別硬限制 |
| 付款 → 查單 → 超時 → 退款 | provider 快照、回跳查單、重複事件、晚到付款、退款 Outbox | 既有離線回歸通過；外部服務與併發未在此驗證 |
| 團購投票 → 開團 → 付款 → 成團 → 取貨 | 人數／已付款數量、核心條件鎖定、截止結算、取消 | 發現 BF-01、BF-06 |
| 便當 → 時段 → 選項 → 收款 → 核銷 | 訂購時限、時間重疊、退單審核、現場收款 | 既有離線回歸通過；全域背景工作受 BF-02 影響 |
| 社務 → 活動／治理／結餘 | 出席補登、多選表決結算、期間分配唯一性 | 發現 BF-02、BF-04、BF-05 |

## 優先修正

### BF-02／P1：一筆到期多選治理提案會中斷後續背景工作

- **狀態：已離線重現。** 建立有至少一票的多選提案，投票截止後，以新的資料庫 session 執行 `_reconcile_member_proposals()`，得到 `MissingGreenlet`。
- **位置：** `backend/app/jobs.py:592` 只 eager-load `MemberProposal.votes`；`backend/app/v2_domain.py:148` 卻讀取未載入的 `proposal.options`。
- **影響：** `reconcile_once()` 在 `backend/app/jobs.py:149` 執行此步驟，之後才處理活動、便當結算、每日場次與 Outbox（149–167 行）。該筆提案未完成時，後續週期仍可能重複卡住，退款、發票與通知工作因此延後。這是程式路徑可確認的連帶影響；沒有聲稱正式環境已發生停擺。
- **建議：** 在結算查詢載入 `MemberProposal.options`，並用全新 session 的多選提案截止測試保護。背景批次另應隔離單一領域失敗，避免一筆社務資料阻斷商務 Outbox。

### BF-01／P1：已成團且售罄的團購，退款釋出名額後仍不能購買

- **狀態：已離線重現。** 已確認成團、供應 5 份、已付款 5 份、截止尚未到；退款 1 份後，`paid_quantity=4`，但 `intake_status=full`。新買家再加入 1 份，收到「此團目前未開放加入」。
- **位置：** `backend/app/domain.py:224` 的 `remove_paid_quantity()` 只處理 `pending_confirmation` 跌破門檻；沒有重新計算 `confirmed + full` 的接單狀態。`backend/app/domain.py:180` 仍擋住加入。
- **影響：** 畫面可能顯示有剩餘數量，實際卻無法下單；空出的名額無法再售出。
- **建議：** 退款後統一重算接單狀態：已確認成團、未截止且有容量時恢復開放；截止後維持關閉。補已確認／待確認、截止前／後、滿額／非滿額的狀態轉移案例。

### BF-06／P1：團購換商品後，舊訂單仍能付款並占用新團購名額

- **狀態：已離線重現。** 買家加入商品 A、100 元團購並取得未付款訂單；尚未建立付款保留時，管理員將團購改為商品 B、200 元；原商品 A 訂單仍可建立 100 元付款頁。
- **位置：** `backend/app/routers/groups.py:334` 僅以首筆付款或有效保留判斷核心條件能否修改；`backend/app/integrations/payment_service.py` 的 `create_payment_attempt()` 團購分支（本次修復後約 710–744 行）只驗證狀態、截止及容量，未核對訂單與團購版本／目標。
- **影響：** 團購目前販售商品與已接受付款的訂單商品不一致，管理員統計、供應準備及履約無法確定應交付 A 或 B。此問題不只是一般的歷史價格快照。
- **建議：** 團購核心資料加入版本；建立付款保留時驗證版本。管理員修改商品／套組或價格後，舊未付款訂單應明確作廢或要求重新試算確認；已有付款保留仍不可變更。

### BF-04／P1：相同會計期間只要改標籤就能再次確認結餘

- **狀態：已離線重現。** 同期間只有一筆 100 元社員已付款訂單，以「本期」與「本期重送」分別呼叫結餘確認，會建立兩份、共 200 元分配紀錄。
- **位置：** `backend/app/routers/cooperative.py:184` 僅檢查 `FiscalYear.label`；`backend/app/models.py:2650` 亦只有標籤唯一約束，沒有期間重疊約束。
- **影響：** 同一交易貢獻可重複列入不可逆分配紀錄。重現只建立本地分配紀錄，並未實際發放款項。
- **建議：** 以會計期間識別正式分配，禁止相同或重疊期間重複確認，並在資料庫層提供併發保護。重算與更正應走獨立、留痕的調整流程，不能靠改標籤重新確認。

## 操作流程需調整

### BF-03／P2：退單待審仍可進入備貨，之後管理員卻無法核准退單

- **狀態：已離線重現；是否凍結履約屬產品政策決策。** 一般商品已付款、待處理時申請退單；管理員仍可按「開始備貨」；之後核准同一退單會得到 409，要求先拒絕申請。
- **位置：** `backend/app/routers/orders.py:100` 待審僅移除 `cancel/refund` 動作；`backend/app/routers/orders.py:696` 推進履約沒有檢查退單待審；`backend/app/routers/orders.py:587` 審核再次套用只允許待處理取消的限制。
- **影響：** 客戶以為退單已進入處理，工作人員卻可繼續備貨並使審核失效。待審建立處（537–561 行）與駁回處沒有通知工作，管理員或買家須自行刷新才知道結果；腳本確認送出時沒有建立 App 通知。
- **建議：** 明確選一套規則：待審暫停付款／備貨／出貨，或允許繼續但顯示明確衝突提醒與處理順序。建議管理員先完成退單審核再備貨；送出與審核結果均發通知。不要把「取消成功」與「已送出退單申請」混用。

### BF-05／P2：活動一結束，自動缺席會讓工作人員無法補登實際出席

- **狀態：已離線重現。** 活動結束後背景程式把未核對名單改成 `no_show`；工作人員稍後補登真實出席，API 回 409「此報名無法標記出席」。
- **位置：** `backend/app/jobs.py:656` 自動將 `registered` 改為 `no_show`；`backend/app/routers/community.py:616` 只接受 `registered` 狀態的出席標記。
- **影響：** 紙本簽到或活動結束後才輸入的真實出席無法修正，社員少拿活動積點。既有活動也沒有可留痕修正出席的路徑。
- **建議：** 區分「尚未核對」與「確認缺席」，或提供管理員填原因的更正入口；出席更正與積點補發／沖回需一起處理並保持冪等。

## 建議的使用者順序

1. **先確認能買。** 商品列表、詳情與試算共用可售資格；任何限制在按下結帳前說明。庫存、開放時段與銷售通路分開表示，避免非便當被誤當成未開放。
2. **一次確認交易內容。** 一般商品選取貨點、團購看成團條件、便當選日期與時段；確認後固定商品、價格、稅別與規則版本，再保留名額並付款。
3. **付款後給單一進度。** 清楚區分「等待付款結果」「已付款」「待成團／備貨」「可取貨」；回跳不能直接假設付款成功。
4. **例外先處理再履約。** 退單待審要對買家與工作人員可見；確認退款與退款完成分開。取消後重新計算可售名額，讓剩餘商品能繼續販售。
5. **保留可追溯的更正。** 活動出席、現場收款、發票與年度結餘都要保留原紀錄及更正原因，不以刪除或重做正常流程補救。
