日期：2026-10-31。分支 `codex/remediation-completion`，基於 `679d659`；本批為本機修復及驗證，尚未部署。整案待辦與正式驗收以 [追蹤表](REMEDIATION_STATUS.md) 為準。

## 修正行為

| 項目 | 本批變更與保留的行為 |
|---|---|
| 積點帳戶 D02 | 三處初始化共用原子 UPSERT 與每帳戶列鎖；helper 不提交或回滾呼叫者交易。首次徽章定義也改為只新增缺少項，保留自訂內容。 |
| 通知 D03 | 通知按用戶／事件／dedupe hash 唯一，通知與 Email 意圖在同一交易保存；外部接受後結果不明先隔離，不自動改供應商重寄。詳見 [寄送契約](NOTIFICATION_DELIVERY.md)。 |
| 開放共同購買提案 D04 | 同一商品／套組的開放提案以目標列鎖與部分唯一索引防重。本人可恢復原案，其他人的私人待審內容不外洩。 |
| 入社查詢 D05 | 將逐筆查詢改為按頁批次讀取；空查詢每頁 25 筆由 152 降至 8 次 SELECT。保留全欄位結果、Unicode 子字串、排序、精確總數與權限。 |
| SQLite 外鍵 D06 | 應用 engine 與共用測試 factory 啟用真外鍵；修復 13 個無效 fixture，願望連結不存在的商品／共同購買在寫入前回 422。 |
| 共同購買 OPS02–04 | 新 join 帶 UUID／總額／完整報價指紋；同一送單恢復先於關店或變價檢查。新訂單保存核心條件，改商品後的舊單不能付款或改量；晚到舊款不計新團，走原退款意圖。 |
| 出席更正 OPS05 | 已自動標缺席後可填原因及預期舊狀態更正，並留稽核；以追加積點補償還原原始額度，包括歷史 80 點，不改寫流水或付款代次。 |

入社私密欄位的任意子字串搜尋仍需掃描解密候選；已採串流與當頁快取，沒有新增姓名明文索引，也沒有宣稱消除這個 O(N) 成本。SQLite 的原始 migration engine 不因應用 factory 修改而一律開啟 FK；遷移另外執行真資料保留與約束驗證。

## 舊資料與金流邊界

- 0042 遇到既有開放提案重複時先停止，不能刪歷史案讓索引通過。
- 0043 對既有通知選最早的同鍵紀錄，其他歷史紀錄保留；舊未關聯的 Email 意圖不猜配對、不自動重寄。舊 producer／worker 的交接順序見寄送契約。
- 0044 只加 nullable 訂單核心條件指紋，不假造歷史契約。舊 NULL 單只可驗證原商品／套組身分；相同目標保留原價續付，不宣稱能完整還原當年全部條件。
- 新 UI 的報價指紋包含運費，join 初始訂單仍先記商品小計，原物流選擇再寫運費；不以兩階段不同金額誤擋配送。
- 原 attempt 尚未查明時保留名額，禁止管理員更改核心條件；若舊版本已留下條件不一致又付款不明的資料，訂單頁優先顯示待核對，不能引導再次購買。
- 原付款已證實未付後可合法改團；之後晚到的舊成功款只產生原 attempt 的退款責任，不重占新團名額、不自動發送外部退款。
- 同 key 恢復已付款、已取消、已改量或條件失效的訂單時回原紀錄，不暗中換 key 或再次開付款。新 key 必須由使用者重新確認後產生。

## 驗證與失敗紀錄

完整整合首輪為 2,586 通過／3 失敗，原始結果保留，沒有選擇性刪除失敗：

1. 舊 Email 測試將「嘗試 8 次且無寄送證據」視為可直接重送；現在先驗無確認回 409，再帶明確風險確認才成功，原原因／隱私／不可重試發票通知斷言保留。
2. 遷移單頭測試原只期待 0043，更新為 0044 並驗實際線性鏈。
3. 套組停用測試將一般商品單改成套組單卻仍保存商品來源；補正真正的套組品項關聯，保留減量成功／加量拒絕的原驗收。
